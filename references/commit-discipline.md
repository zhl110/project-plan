# 提交纪律（commit-discipline）

> 本文件在**项目要落盘代码 / 文档到版本库、或任何"提交类"动作**时加载。方法论取自 `agency-agents/engineering/engineering-git-workflow-master`（Git Workflow Master）——它专管"提交类"：原子提交、约定式提交、安全协作。这里把它收敛成通用纪律，去掉与单项目无关的团队分支策略细节。

## 适用场景

- 把本次动作的产出（代码 / 文档 / 配置）提交进 git 或任何版本库。
- 把计划文件（PRD/PLAN/progress/AGENTS）的变更提交进项目仓库。
- 多 Agent / 多会话协作时，保证历史可读、可回滚、不互相覆盖。

> 纯本地文件产出、不进版本库的，不需要本纪律；但只要"提交"，就遵守下面四条。

## 四条核心纪律

### 1. 原子提交（atomic commit）
每个提交只做**一件事**，可独立回滚。
- 不把"改 bug + 顺手重构 + 加文档"塞进一个提交。
- 一个逻辑动作 = 一个提交；多个文件为同一目的改，可同提交。
- 判定：能否用一句话说清这个提交"做了什么、为什么"？说不清就该拆。

### 2. 约定式提交（conventional commits）
提交信息遵循 `type: subject` 格式，`type` 取：
- `feat:` 新功能 / 新文件产出
- `fix:` 修 bug / 修正错误
- `docs:` 文档 / 计划文件 / AGENTS 的纯文字变更
- `refactor:` 重构（不改外部行为）
- `test:` 测试相关
- `chore:` 杂务（依赖、配置、脚本）
- 正文/脚注写**为什么**（动机），不只写做了什么。

> 计划文件（PRD/PLAN/progress）的日常追加多属 `docs:` 或 `chore:`；不要把"需求变更"写成 `feat:`。

### 3. 不破坏共享分支
- **绝不**对共享分支（main / master / 他人正在用的分支）强制推送。
- 必须强推自己的分支时，用 `--force-with-lease` 而非 `--force`。
- 合并 / 推送前先 `fetch` + `rebase` 到目标最新，不在过期基础上叠提交。
- 危险命令（reset --hard / push --force / clean）执行前先确认目标分支、先备份。

### 4. 提交前同步上下文
- 提交前先拉取远端最新，解决冲突再提交，不制造"后来才发现覆盖别人"的提交。
- 多人 / 多 Agent 同仓库时，提交粒度对齐"一个动作一条"，避免大包提交吞掉他人留痕（参见 AGENTS.md 协同约定）。
- progress 这类"每轮都在追加"的共享文件，提交前先读尾部、只提交自己这条、不与他人当轮改动混批。

## 与本项目其他纪律的关系

- 提交是 `runtime-loop` 里"动作完成"的落盘动作；本纪律约束"怎么落盘"。
- progress.md 的会话流水是"为什么 + 涉及文件"，与提交信息的"为什么"互为印证。
- 提交失败 / 历史污染，按 `runtime-loop.md` 异常表"外部操作失败"分支处理（先备份、再修复、不裸奔）。

# 建档规则：四件套生成与合格标准

> 本文件在**建档 / 补文件阶段**加载。建档指：项目尚无完整档案时，先按项目性质评估定类型，再按各自「生成规则 + 合格标准」产出对应文件集；补文件指：跟踪模式下某文件缺失时单独补。

## 创建模式（项目缺档案时）

先按 SKILL.md「项目性质评估」定类型：
- 交付型 → 生成四件套（AGENTS + PRD + PLAN + progress）
- 运营型 → 仅生成 AGENTS.md + .plan/progress.md（**不生成 PRD / PLAN**）

> 推荐用 `scripts/scaffold.py <项目根目录> [--type delivery|operation]` 一次性**非破坏性**生成对应文件集（脚本保证"已存在绝不覆盖"）；下方步骤是等效的手写流程，二选一。

### 交付型
1. **AGENTS.md**：若项目根**不存在**则创建（从 `assets/AGENTS.md` 读取骨架写入）；已存在则跳过并报告路径，绝不覆盖。
2. **.plan/ 三件套**：若 `.plan/` 目录不存在则创建；将 `assets/` 中的 `PRD.md` / `PLAN.md` / `progress.md` **逐一写入，仅当该文件在目标位置不存在时才写**，已存在的不动。
3. 与用户确认需求后填 PRD（背景 / 目标 / 需求 / 验收）。
3.5 **文件布局规划**（详见 `file-layout.md`）：PRD 确认后、PLAN 动手前，按复杂度选强度（S 一句话 / M 列核心 / L·XL 完整表），产出 B 层快照（区块切分 + 目录结构 + 产物落点表），并沉淀 A 层规则（命名 / 临时文件隔离 / 先登记再创建）进 AGENTS.md；B 层写进 PLAN「文件布局」段，标「最后核对」时间戳。
4. 填 PLAN（阶段 / 步骤 / 决策 / 验证 / 风险 + 文件布局段），并跑一次「预执行自检清单」（见 `plan-structuring.md`）。
5. 填 progress 的元信息 + 上下文压缩（见 `progress-spec.md`）。
6. 展示计划，用户确认后再执行。

### 运营型
1. **AGENTS.md**：若项目根**不存在**则创建；已存在则跳过并报告路径，绝不覆盖。
2. **.plan/progress.md**：仅写这一个（`.plan/` 目录不存在则建）；`PRD.md` / `PLAN.md` **不生成**。
3. 填 progress 的元信息 + 上下文压缩（见 `progress-spec.md`）——运营型无"阶段验收"，上下文压缩聚焦"当前在做的长期事项 / 已沉淀规则 / 待办"；**并填写 progress「下一步 / 待办」段**（运营型循环取任务的唯一入口，见 runtime-loop 简化循环）。
4. 展示项目规则与进度机制，用户确认后再执行。

## 补录模式（项目已开工但缺档案时）

触发：项目根已有代码 / 产物 / git 历史，但无档案；或档案是空模板（判定：标题 / 占位符原样未填、无任何项目特有内容、无变更记录——三者任一即视为空模板，按缺档案处理）。此时档案是**反向侦查出来的，不是模板填出来的**。正在做这个项目的 agent 对项目本身已有了解，这是合法信息源——与磁盘证据分级使用。

**信息源分级**（每处补录内容标注来源层级）：
- **L1 磁盘证据**：git log、依赖清单、构建脚本、目录结构、已有文档——可直接写。
- **L2 agent 已知**：本轮工作中已掌握的项目情况——可写，标注「来自对话」。
- **L3 推不出**：标「待用户确认」，不编造；禁写"应该 / 大概"。

**流程（侦察 → 反写 → 哨兵）**：
0. **先补骨架**：跑 `scripts/scaffold.py <项目根> --type <判定类型>` 非破坏生成缺失的骨架文件（已存在的不动），再反向填充——复用标准格式，不手搓结构。
1. **派侦察兵子 agent**（只读）：盘点项目根——git log（提交主题与时间线）、目录结构、依赖清单、README / 已有文档、构建入口，产出「证据清单 + L1/L3 分类」；**并反向推导当前文件布局，标注是否散乱 / 随手建（无规划、产物与目录名不符、临时文件混进源码树），给整理建议**。agent 自身已了解的项目情况归 L2，不经侦察兵。
2. **反向撰写**（先按项目性质评估定文件集，再逐文件反推）：
   - AGENTS.md：只写 L1 / L2 已验证的技术栈与约定；推不出的约定标待确认。
   - PRD：从已有功能反推问题陈述 / 目标 / 验收；L3 标「待用户确认」。
   - PLAN：当前阶段按项目现实落在词表上（见 `plan-structuring.md` 回溯判定），已完成工作归入完成清单并注明「回溯标记」；下一步只填一个真实待办。
   - progress：**不伪造历史**。首条写「回溯建档」条目（何时建档、基于什么证据、覆盖哪些阶段），此后流水从现在开始记。
3. **哨兵核验**（必过，见下节）。
4. 展示补录结果 + 差异清单（L1 / L2 / 待确认各几条），用户确认后生效。

**「回溯建档」首条样例**（progress 会话流水第一条，此后从现在开始记）：
```markdown
- [2026-10-27] 回溯建档 → 为什么：项目开工时未用本 skill，补录档案以规范后续协作 → 涉及：AGENTS.md(新建) .plan/PRD.md(新建) .plan/PLAN.md(新建) → 证据：git log 34 次提交(至 2026-09-15)、pyproject.toml、docs/ 目录；L1 证据 12 条 / L2 来自对话 5 条 / 待确认 3 条（见 PLAN 待确认清单）→ 验证：哨兵核验 PASS → 错误：无
```

## 哨兵子 agent（建档 / 补录质量门禁）

创建、补录建档完成后，**必须**派一个独立只读子 agent 核验，主 agent 自查自评不算数（自己建的档自己验必放水，与 DARWIN 自评偏差同源）：

- **核什么**（对照内联的「合格标准」逐项）：
  1. 结构与必填段齐全（每文件按各自合格标准）。
  2. 状态真实：PLAN 当前阶段 vs 项目现实——**限范围核对**：git log 只看最近 20 条、交付物只看顶层目录，不翻全量历史/深目录；无造假完成态。
  3. 无编造：progress 无伪造历史流水；补录中标 L1 的内容**抽查 ≤2 条且只验文件名是否存在**（不深读内容），核对是否真在磁盘上对得上。
  4. 红线合规：AGENTS 非破坏、`.plan/` 无杂物、交接结构完整。
  5. 布局镜像现实：B 层快照（PLAN 文件布局段）vs 实际目录树——**限范围**：目录树只看顶层 2 层；不符则更新文档匹配现实（doc follows reality），或列脏文件进待清理清单。
  > **范围限定的目的**：把"翻遍仓库"的耗时砍掉，提速不降主干质量——跨文件一致性（项 1/4）、必填项、红线全保留；仅放过极低频的"深层/古老磁盘错位"，此类错后续执行循环会暴露，不靠建档哨兵独担。L/XL 大项目若担心深层错位，可在派哨兵时放开范围（保留深扫开关）。
- **怎么派**（判据必须内联，禁止指路自读）：哨兵提示词**必须**把下方各文件的「合格标准」条目（AGENTS ①–⑤ / PRD ①–⑦ / PLAN ①–⑩ / progress ①–⑥，见本文件「文件生成规则与合格标准」节）**整段复制进提示词**，让子 agent 拿来即用。**严禁**只写"去读 `references/generate-files.md` 自取判据"——那样子 agent 会先把 197 行含大量生成规则/范例的文件读一遍、再顺藤摸瓜读更多，纯属磨蹭且易跑偏。内联=整段复制，不是摘抄，保证一条不漏。侦察兵同理（只读约束 + 明确产出格式）。
- **怎么给结论**（固定短模板，禁散文）：格式**强制**为——`结论：PASS` 或 `结论：未达标｜<文件> + <第几条不合格> + <应补什么>`（多条逐行列）。**不得**写大段分析/散文式报告，省时且不损失信息量。未达标 → 主 agent 补齐 → 复检，**通过才算建档完成**；复检最多 2 轮，仍未过→停手，带未达标清单交用户裁决，不无限循环。**注意**：此「2 轮」是「建档哨兵核验」的复检上限，与 `review-gates.md` 阶段门禁的「交付物最多 3 轮修订」是**两套独立限制**，不要混为一谈。
- **结论留痕**：哨兵结论（PASS / 未达标清单 + 轮次）记入 progress 会话流水，作为「建档完成」的证据链。
- **先后顺序**：哨兵通过后，才向用户展示档案并等确认；不把未核验的档案拿去打扰用户。
- **S 级豁免**：复杂度 S 级（≤3 文件单领域）的项目，不派哨兵子 agent——对照各文件合格标准自检即可，成本与收益相称。
- **无子 agent host 的降级**：host 不支持派子 agent 时，**不得跳过核验**——降级执行：能开独立新会话则在新会话中按合格标准逐项核对并留痕；不能则主 agent 在建档动作完成后隔开一步、明确切换到核验角色再逐项核对（核对结论同样记入 progress）。侦察兵同理降级：主 agent 自行盘点磁盘证据，但必须落盘盘点清单（作为 L1 证据的溯源基础）。
- **跟踪模式不强制**：档案已存在，只改差异处，改完对照对应文件的合格标准自检即可。

## 非破坏性验证（冒烟）

scaffold.py 是「绝不覆盖」承诺的唯一承载者，每次改完脚本或模板后手动验证一遍：

1. 建临时目录 `T`（跨平台：Linux/macOS 用 `/tmp/pp_smoke`；Windows 在 Git Bash 下 `/tmp` 通常可用，或改用 `$TMPDIR` / `C:\Users\<你>\AppData\Local\Temp\pp_smoke`），预先放入一个已有 `AGENTS.md`（随便写点内容）。
2. 跑 `python scripts/scaffold.py "$T" --type delivery`。
3. 断言：①脚本报告「已跳过(已自定义，受保护)」且 `T/AGENTS.md` 内容**未被改动**；②`.plan/` 三件套被正常生成（报告「已生成」）；③退出码为 0。
4. 再跑一次同命令，断言自定义文件仍「受保护」、空模板文件标「未填写的空模板，可走补录模式重填」，无静默覆盖、无报错。
5. 清理临时目录（`rm -rf "$T"` 或手动删除）。

`--force-root-agents` 例外：传入后第 1 步的 `AGENTS.md` 应被模板**覆盖**（这是唯一允许覆盖的显式开关，非静默）。

> 空模板信号：第 4 步若某文件报「未填写的空模板」，说明它仍是 scaffold 产出的未填占位模板——路由上等同缺失，应走补录模式反写或直接删掉重跑，不要把它当「已有档案」接手。

## 跟踪模式（已有档案时）

1. 读 `AGENTS.md` → 读 `.plan/PLAN.md` → 读 `.plan/progress.md`（含上下文压缩与交接上下文）。
2. 从交接上下文的断点继续。
3. 每完成一个动作 / 阶段，按纪律更新 PLAN 状态与 progress（详见 `runtime-loop.md`）。

## 文件生成规则与合格标准

> **PRD.md / PLAN.md 仅交付型需要**；AGENTS.md 与 progress.md 两类项目都要。运营型写文件时跳过 PRD/PLAN 两节。

建档时每个文件按「生成规则（写什么、怎么写）」产出，并用「合格标准（自检清单）」校验；不满足则补全。**约束（禁项）** 是红线，违反即不合格。

### AGENTS.md（项目根）
- **用处**：回答"这个项目有哪些规则 / 技术栈 / 目录约定？"——agent 开工前读、执行中写回。
- **生成规则**：项目目标、技术栈、A 层目录 / 文件约定（稳定规则：命名、禁随手建临时文件、新产物先登记再创建）、通用工作纪律、本项目特有规则；**具体的当前目录树属 B 层可变快照，写进 PLAN 架构段而非此处**（详见 `file-layout.md`）。规则用祈使句写可执行项。
- **合格标准**：①有项目目标 ②列出技术栈与 A 层目录约定（稳定规则，非当前树）③至少 1 条工作纪律 ④每条规则为可执行祈使句（非描述）⑤每条规则为当前生效条文（无「已弃用 / 旧版 / 之前是」标注，对齐红线 #18）。
- **约束**：不写进度（那是 progress）、不写产品背景（那是 PRD）；agent 写回只追加不删用户已写规则；更新规则直接改 / 删条文，不保留「已弃用」标注、不补变更留痕（见红线 #18）。

### AGENTS.md 渐进式披露（规则跨多主题 / 过长时）

> 本 skill 对 SKILL.md 自身用渐进式披露（地图 → `references/` 按需加载）；**项目自身的 AGENTS.md 同样适用**——复杂 / 长期项目的规则会跨很多方面（CI、编码风格、命名、外部依赖、领域约定…），全堆在一个文件里会又长又难维护，且每次开工都整篇读入浪费上下文。

**触发**：AGENTS.md 涉及 ≥5 个独立主题，或行数 >~120 行 → 转入「索引 + 子文件」模式。

**结构**：
- `AGENTS.md`（项目根）= 薄入口，仅含：项目目标 + **规则索引表**（`| 主题 | 文件 | 何时加载 |`）。
- `AGENTS.d/<topic>.md`：每个主题一个文件，内容为可执行规则（祈使句）。

**加载纪律**（镜像 skill 自身原则）：开工先读 AGENTS.md 索引（薄）；执行某任务时，仅当任务触及某主题才加载对应 `AGENTS.d/<topic>.md`，**不整篇读入 AGENTS.md 全部子文件**。
**写回纪律**：沉淀出的规则追加到对应主题子文件；仅当新增主题时才在 AGENTS.md 索引加一行，不重写索引。
**约束**：`AGENTS.d/` 子文件也是项目规则一部分，受"活规则库"纪律约束（追加不删、更新规则直接改 / 删条文，不保留「已弃用」标注、不补变更留痕，见红线 #18）；`.plan/` 与 `AGENTS.d/` 职责不同——前者放计划/进度，后者放规则，互不混放。

### PRD.md（.plan/，仅交付型）
- **用处**：回答"做什么、为谁做、做到什么程度算成功？"
- **生成规则**（吸收 `product/product-manager` 的 PRD 结构与纪律）：
  - **① 问题陈述**：先写"为谁解决什么具体问题"，再谈方案——**领着问题走，不领着方案走**。
  - **② 目标与成功指标表**：`| 目标 | 指标 | 当前基线 | 目标值 | 衡量窗口 |`，每目标可量化。
  - **③ 非目标（Non-Goals）**：显式列出"本轮不做什么"，遏制范围蔓延（scope creep）。
  - **④ 用户故事 + 验收（Given-When-Then）**：每条需求配 `Given [上下文] When [动作] Then [期望]` 可测验收，禁"体验好"之类主观词。
  - **⑤ 风险表**：`| 风险 | 可能性 | 影响 | 缓解 |`，与 PLAN 风险登记册呼应。
  - 背景、目标用户、约束假设照旧。
- **纪律**：**先写验收再写需求**（验收想不清楚 = 需求没想清楚）；任何变更请求显式记录"接受 / 延后 / 拒绝 + 理由"，不静默吸收。
- **合格标准**：①需求表无空项且每条有优先级 ②验收标准可测试且含 Given-When-Then ③非目标已列 ④成功指标表有基线/目标/窗口 ⑤风险表已列 ⑥有「变更记录」段 ⑦背景与目标一致。
- **约束**：不写实现细节（那是 PLAN）；验收必须可测；需求变时补变更记录并联动 PLAN。

### PLAN.md（.plan/，仅交付型）
- **用处**：回答"怎么做、分几阶段、到哪了、怎么验证、踩过什么坑？"
- **生成规则**（吸收 `project-management-project-shepherd` 的风险/干系人 + `handoff-templates` 阶段门禁）：
  - **文件布局 / 产物落点（B 层可变快照）**：动手前规划、随结构演化刷新，标「最后核对」时间戳（详见 `file-layout.md`）；不是死规则，改动正常刷新，大型项目可渐进式披露到 `AGENTS.d/layout.md`。
  - 目标、当前阶段（取自 9 阶段词表，见 `plan-structuring.md`）、下一步（单动作）、最后更新。
  - **分阶段清单**：每阶段带状态（`pending`/`in_progress`/`complete`）+ **验收字段**；每任务项带「为什么」、owner（谁负责）、指标/时间窗、子任务 3–7 且动词开头。
  - **风险登记册**：`| 风险 | 可能性 | 影响 | 缓解 | 负责人 |`，与 PRD 风险表呼应、不重复。
  - **干系人**：`| 角色 | 是谁 | 关注点 |`，至少列赞助方与执行方。
  - **阶段门禁**：每阶段切出前过 `references/review-gates.md` 的门禁（判据来自该阶段验收）；门禁不通过不过阶段。
  - 关键决策表、验证结果表、错误记录表照旧。
- **合格标准**：①有目标 ②当前阶段明确 ③「下一步」唯一且为单动作 ④分阶段清单每阶段有状态+验收，每任务项带「为什么」+owner+指标/时间、子任务数 3–7、动词开头 ⑤有风险登记册 ⑥有干系人 ⑦有验证结果表 ⑧有错误记录表 ⑨「最后更新」有值 ⑩有「文件布局 / 产物落点」段且标注为可变快照（标「最后核对」时间戳）。
- **约束**：不写背景（那是 PRD）；"下一步"只填一个动作；状态禁造假（没做不能标完成）；阶段切换即更新，切换前过门禁；错误/验证汇总真相以本文件为准；文件布局为 B 层可变快照，须镜像现实（随结构刷新，禁与真实目录树脱节）。

### progress.md（.plan/）
- **用处**：回答"这轮实际做了什么、产出什么、验证了没、错在哪、接手的 Agent 从哪接着干？"
- **生成规则**：元信息 + 上下文压缩（用户偏好 / 架构 / 文件索引 / 已确认决策 / 环境）+ 交接上下文（对齐 `handoff-templates` 标准交接结构）+ 会话流水（动作 → 为什么 → 涉及文件 → 验证 → 错误）+ 变更日志。
- **交接上下文结构**（吸收 `strategy/coordination/handoff-templates`，暂停 / 换人必填，假设接手者一无所知）：
  - **From / To**：本 Agent（或"用户本人"）→ 接手方（下个 Agent / 未来的自己 / 用户）
  - **当前阶段**：所处阶段 + 断点（停在第几步 / 哪子任务）
  - **相关文件**：`路径 — 含什么`（改动 / 产出 / 待读）
  - **依赖 / 约束**：本工作依赖什么就绪、有哪些技术 / 时间 / 资源约束
  - **已完成 / 未完成**：具体产出物 + 按步骤列的未完成项
  - **关键发现 / 注意事项**：特殊逻辑、环境坑、踩过的雷
  - **下一步建议**：明确起点（与 PLAN「下一步」一致）
- **合格标准**：①上下文压缩已填可填部分（新建项目允许基于需求预填要点：用户偏好 / 目标 / 约束；架构与文件索引可标"待项目产出后补充"，但不得整段留占位不写）②交接上下文完整且含上述 7 项（暂停必填，非暂停可为骨架）③每次动作有会话流水，且流水含结构化「涉及文件」（修改 / 新增 / 删除 + 路径）④有变更日志 ⑤`.plan/` 只放四件套 ⑥「下一步 / 待办」段已填——**运营型此项为循环取任务入口、必须填**；交付型此项为 PLAN「下一步」镜像即可。
- **约束**：只追加不回改历史条目；不写背景 / 规则；纯问答也补"无动作"；`.plan/` 只放四件套，不得塞代码 / 产物。

## 填法范例

写每个文件前对照 `references/example-filled.md` 的完整样例，不凭空起炉灶。

## 运营型最小样例（AGENTS + progress）

运营型不生成 PRD/PLAN，档案只有两个文件，够用即可：

**AGENTS.md**（项目根）
```markdown
# 项目规则（长期任务）

## 目标
长期维护本仓库的 CI 配置，保证构建稳定、增量可复现。

## 工作纪律
- 改 CI 前先在分支验证，不直推 main。
- 每次改动记一条 progress，含"为什么"。
```

# 进度与交接

# 审核与阶段门禁（review-gates）

> 本文件在**交付型项目做阶段验收、产物审核、或决定"能否推进下一阶段 / 能否算收工"**时加载。方法论取自 `agency-agents/testing/testing-reality-checker`（默认不通过、证据至上）与 `testing/testing-evidence-collector`（验收须有证据），并吸收 `strategy/coordination/handoff-templates` 的**阶段门禁（Phase Gate）**与**升级根因**结构。已剥离两者大量"网页 QA / 截图 / dark mode"特定内容——本 skill 是通用规划器，审核对象是"计划文件与交付物"，不是网页像素。

## 一、审核精神（来自 Reality Checker / Evidence Collector，抽象化）

1. **默认不通过（default to "NEEDS WORK"）**：任何阶段验收、产物审核，先假设"还不行"，直到有证据推翻。不要把"我自己写的、应该没问题"当验证结论。
2. **验收须有证据，不靠自报**：每条验收标准都要能拿出"怎么验证的"——跑通的命令、读到的输出、对照 spec 的逐条勾选。无证据 = 未通过。
3. **首版需 2–3 轮修订**：交付物第一版通常要迭代；把"初版通过"当成异常，把"需要打磨"当成常态。评分诚实（基本 / 良好 / 优秀），不给虚高。
4. **硬性失败触发（任一即 FAIL，不含糊）**：
   - 交付物破了核心链路（本该有的东西不可用 / 接手者 30 秒看不懂）。
   - spec 要求未实现（计划写了但没做 / 做偏）。
   - 验收声明与证据矛盾（声称达成但证据不支持）。
   - 改动未经备份就覆盖了他人 / 历史文件（违反非破坏性纪律）。

## 二、阶段门禁（Phase Gate，来自 handoff-templates）

交付型 PLAN 的每个阶段切换前，过一道门禁。门禁不通过不过阶段。

```markdown
## 阶段门禁：<阶段名> → <下一阶段名>
| # | 门禁判据 | 阈值 / 标准 | 结果 | 证据 |
|---|----------|-------------|------|------|
| 1 | <判据，如"核心功能跑通"> | <标准> | ✅PASS / ❌FAIL | <证据：命令/输出/对照> |
| 2 | <判据> | <标准> | ✅/❌ | <证据> |

文档顺延：<本阶段哪些产物带入下阶段>
下阶段约束：<本阶段暴露的限制 / 风险>
```

- 门禁判据从 PLAN 该阶段的「验收」字段来；没有验收字段的阶段不准切。
- 任一 ❌ → 不切阶段，返回补；补完重过门禁。

## 三、验收裁决模板（QA 式，抽象自 handoff-templates）

阶段 / 产物审核结束时，出一份简短裁决：

```markdown
# 验收裁决：<阶段 / 产物>
**裁决**：PASS ✅ / FAIL ❌ / NEEDS WORK
**尝试次数**：第 N 次（首版算 1）
**证据**：
- <判据1>：<PASS/FAIL + 证据引用>
- <判据2>：<...>

**待修项**（FAIL/NEEDS WORK 时）：
1. <问题> — 期望：<spec> 实际：<现状> — 证据：<引用> — 改哪：<文件>
2. <...>

**下一步**：PASS → 过门禁进下阶段；FAIL → 回到本阶段补，最多 3 轮，第 3 轮仍 FAIL 走升级。
```

## 四、升级与根因（第 3 轮仍 FAIL 时，抽象自 Escalation Report）

```markdown
# 升级报告：<阶段 / 产物>
**失败史**：
- 第1轮：<问题+改动+仍FAIL原因>
- 第2轮：<...>
- 第3轮：<...>

**根因分析**：<为什么一直过不了——范围错估 / 方法错 / 缺依赖 / 验收判据本身不合理>
**建议处置**：[重派] / [拆更小子任务] / [改方案] / [接受当前并记限制] / [延后]
**影响**：<阻塞哪些下游 / 时间影响>
**决策方**：<用户 / 编排者>
```

> 升级不是甩锅，是"带着证据把决策权交回人"。对应 `runtime-loop.md` 异常表"审查严重问题 / 改动出错"分支。

## 与本 skill 其他文件的关系

- PRD 的「验收标准」、PLAN 的「每阶段验收」是本门禁的输入；本文件规定"怎么审、怎么判、过不了怎么办"。
- 运营型项目无 PRD/PLAN，不走阶段门禁；运营型只做"改动是否破坏现有规则"的轻量自检（见 `generate-files.md` 运营型）。
- 提交落盘见 `commit-discipline.md`；门禁 PASS 后的提交信息写 `docs:` / `feat:` 并附裁决结论。
